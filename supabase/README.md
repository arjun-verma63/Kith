# supabase/

Database schema, migrations and local development.

## First-time setup

The Supabase CLI is **not** a project dependency — it is a large platform binary
and pinning it in `package.json` buys little. Run it through `npx`:

```bash
npx supabase init      # generates config.toml (committed once it exists)
npx supabase login     # opens a browser, stores a personal access token
npx supabase link --project-ref <ref>
```

For local development you also need Docker running:

```bash
npm run db:start       # Postgres, Auth, Realtime, Storage on localhost
npm run db:reset       # drop, re-run every migration, re-seed
npm run db:stop
```

## Working on the schema

**Migrations only.** Editing the schema in the Supabase dashboard is banned: it
makes local, staging and production diverge silently, and there is no way back.
The dashboard is for reading, not writing.

```bash
npm run db:diff -- add_profiles    # capture local changes as a migration
npm run db:types                   # regenerate src/types/database.ts
```

A schema change is finished when three things are true: the migration is in
`migrations/`, `src/types/database.ts` is regenerated, and the RLS policies for
every touched table have a test in `tests/`.

## Testing the schema

```bash
npm run db:test
```

No Docker, no daemon, no linked project. The harness runs the migrations against
**PGlite** — Postgres 17 compiled to WebAssembly, so it is the real engine with
the real planner and the real RLS implementation. Supabase's `auth` schema and
the `anon` / `authenticated` / `service_role` roles are stubbed faithfully, so
`set role authenticated` in a test is the same thing PostgREST does for a
signed-in user.

Every test is a **negative** case — proof that somebody cannot reach data they
are not entitled to — plus a handful of positive controls. A policy suite that
only checks the happy path passes just as well with RLS switched off, which is
precisely the failure it exists to catch.

Four schema-wide invariants are asserted too, so a future migration that forgets
one fails here rather than in production:

- every table has RLS enabled **and forced**
- no table has RLS on with zero policies (a silent deny-all)
- every `SECURITY DEFINER` function pins `search_path`
- every foreign key is covered by an index

## Rules

1. **Every table gets `ENABLE ROW LEVEL SECURITY` in the same migration that
   creates it.** A table with RLS off is readable by anyone holding the anon key,
   which is a public value. There is no "we will add policies later".
2. **Deny by default.** No policy means no access. Grant the narrowest thing that
   works.
3. **Break policy recursion with `SECURITY DEFINER` helpers**, and pin
   `SET search_path = ''` on every one of them with fully-qualified table names.
   A mutable `search_path` on a `SECURITY DEFINER` function is a
   privilege-escalation vector, not a style preference.
4. **Wrap `auth.uid()` as `(select auth.uid())`** inside policies so Postgres
   caches it as an InitPlan instead of re-evaluating it per row.
5. **Never trust a client-supplied user id.** Ownership columns default to
   `auth.uid()` and are pinned by a `WITH CHECK` clause.

See `docs/ARCHITECTURE.md` §5 for the full security model and the entity list.

## Layout

```
supabase/
├── config.toml     generated by `supabase init`
├── migrations/     timestamped, immutable, applied by CI
└── tests/          RLS suite — runs the real migrations on PGlite
```
